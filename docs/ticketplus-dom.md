# TicketPlus 頁面資料、場次與張數選擇

唯讀入口是 `src/platforms/ticketplus/pageState.ts` 的 `readTicketPlusPage(page)`。
它回傳活動、選票、排隊、資料或付款頁的資料快照，或帶固定原因的 `unknown`。
不點擊、不輸入、不導航、不等待或重試，不比對購票設定，也不判定購票成功。
API、worker、runner、GUI、Klook 程式與 TicketPlus 啟動保護維持原樣。

## 證據來源與限制

來源是本次對話由使用者操作、助理唯讀觀察的單一活動，以及 2026-10-14 再次唯讀核對的活動／選票頁。
活動名稱為「2026孿生姐妹之夜之鬼迷心竅」，場次 2026-10-30 20:00。
活動 ID `0233a891800ffaa343bf8bff73d390e8`，場次 ID `62ecd68cb52728a63ac9cff43172e04f`。
這些是公開活動資訊，不是帳戶或訂單憑證。

`tests/fixtures/ticketplus/pages.ts` 是最小結構重建，不是下載的完整 HTML。
沒有加入網站不存在的票種 data-testid 或加減按鈕 aria-label。
多場次、同名票種、跨頁衝突、資料缺漏等是人工防禦案例，不是已觀察到的實站行為。

資料頁與付款頁本次沒有重新送出購票來復現；使用先前觀察的文字、角色與摘要結構。
資料頁 fixture 的 label/for 關聯重建已觀察的欄位名稱；原始動態 ID 不作選擇器。
付款頁的活動標頭沿用已核對的選票頁結構，仍需下一次實站唯讀複核。
若網站結構不同，reader 回 `unknown`；本機通過不能宣稱已支援所有活動。

## 已觀察的流程與定位依據

| 頁面 | 路徑 | DOM 依據與資料 |
| --- | --- | --- |
| 活動 | `/activity/<eventId>` | 唯一可見 h1；`.sesstion-item` 是網站實際拼字。每列有名稱、日期含星期、時間及「立即購買」button。頁面還有同名 tab，不能當成購票按鈕。沒有觀察到按鈕提供 session ID。 |
| 選票 | `/order/<eventId>/<sessionId>` | `.row.py-1.py-md-4.rwd-margin.no-gutters` 每列是一個票種；名稱是第一欄 `.font-weight-medium` 的直接文字。庫存 span 與價格 div 不屬於票名。 |
| 排隊 | 同上 | 可見 h3「排隊購票中 請稍候」。底層選票頁可能仍在，故 order 先判排隊。消失不代表進入 confirm，也不代表失敗。 |
| 資料 | `/confirm/<eventId>/<sessionId>` | 「聯絡人資訊」、姓名／phone_field／電子郵件欄位、條款 checkbox 與下一步。勾選前下一步停用；勾選後啟用。 |
| 付款 | `/checkout/<eventId>/<sessionId>` | `.stepText.checkedStep` 文字付款結帳；`.row.py-2.py-md-3.no-gutters` 摘要依序為票種、數量、票價、小計；前往付款 button。讀出所有摘要列，不只目標票種。 |

選票頁的活動資訊位於含 `.mdi-calendar` 的 `.text-page-title` 父容器；日期與時間分別在 calendar／clock-outline 圖示的同列兄弟欄位。
隱藏的響應式副本不讀；不把全頁第一個標題或任意日期當成場次資訊。

計數器 `.count-button` 內依序為 minus button、張數 div、plus button。
按鈕本身沒有文字名稱，內含 `aria-hidden` 的 `.mdi-minus`／`.mdi-plus` 圖示。
實作只在同一票種列讀取控制項，未來操作層可用 scoped getByRole("button") 搭配圖示 filter；不能假設 name="＋"。
唯讀快照採一次同步 `page.evaluate` 擷取 DOM，避免跨多次 locator await 混合資料；不模擬點擊。

觀察到學生票 0 張、預售票 1 張時，下一步啟用；這不能單獨證明選對票。
身障票顯示剩餘 0、已售完，且無計數器。
熱賣中沒有確切庫存；輸出 `remainingQuantity: null`，不可補成 0。
`saleStatus: selling` 只代表已辨識的網站文案，不保證有票；`canIncrease` 是獨立的按鈕狀態。
同名票種保留為多列，後續選擇器必須檢查是否唯一。

使用者按更新票數後曾觀察到預售票由 1 回到 0、學生票剩餘 15 變 14、下一步停用。
沒有取得穩定的刷新完成標記，也無法推論庫存減少原因。本階段不執行刷新、不加入順位或重試策略。

## 回傳契約

- 每份結果帶該頁網址讀出的 eventId；order、confirm、checkout 另帶 sessionId，不替换成設定值。
- 選票／付款成功快照必須有活動名稱、真實日期、合法時間與完整的所有票種列。
- 資料頁只回傳欄位 present／hasValue／disabled、條款與下一步狀態；缺聯絡欄位以 present=false 明確表示。kind=information 不代表資料已通過驗證。
- 姓名、電話、Email 的值在瀏覽器內轉成布林值，不回傳至 Node，不記錄 cookie、HTML 或原始 Playwright 錯誤。
- `unknown` 的原因包括 unsupported-url、page-changed、read-failed、conflicting-page、incomplete-data、ambiguous-data。這些都不是售完或最終失敗。
- `queue` 僅適用 order 路徑；checkout 出現排隊或其他頁面殘留標記視為衝突。
- 取得 URL 與 DOM 後再核對瀏覽器 URL；變動即拒絕。結果只代表取樣瞬間，不能保證未來點擊時仍有效，也不宣稱偵測所有同 URL 重繪。
- 不解釋未知 query/hash；目前只接受已觀察的無參數 HTTPS ticketplus.com.tw 路徑。

## 驗證與未涵蓋範圍

本機 Playwright 攔截路由供應 fixture，測試完整值、隱藏副本、重複控制項、錯誤網址、跨頁衝突、資料缺漏、售完與庫存區別，以及讀取前後零 click/submit/input/change 與表單值不變。
測試 expected 手寫，不呼叫正式 parser 產生答案，也不 mock reader。
保留既有 TicketPlus 設定與啟動保護測試。

未實作：登入判斷、更新票數、條款勾選、個資正確性核對、付款核對成功判定、錯誤彈窗恢復、生命週期、API 啟動分流。
未確認：多場次實站版型、購買上限、排隊過期、其他活动實名／問卷／選位要求。

## 活動頁選擇場次

`src/platforms/ticketplus/sessionSelection.ts` 新增 `selectTicketPlusSession(page, settings, options)`。
使用現有 TicketPlus 設定，不新增場次名稱欄位，不修改 Klook、API、worker、runner、GUI 或啟動保護。
傳入的 Page 必須已由使用者手動登入並停在活動頁；此模組不開啟瀏覽器、不檢查 cookie、不代登入、不導航回起點。

流程：

1. 複製並驗證設定，讀取完整活動快照；核對活動 URL 的 eventId 及 eventName。
2. 日期與時間必須恰好對應一列，再檢查該列 buyEnabled。停用列也參與唯一性檢查。
3. 保留該列場次名稱作定位依據；它不是新的設定條件，不要求等於活動標題。
4. 以可見 `.sesstion-item` 的名稱、完整日期（可含星期）、時間限定目標，使用同列 `getByRole("button", { name: "立即購買", exact: true })`。不保留舊索引、不取 first、不 force click。
5. 點擊前重新讀取活動與場次唯一性，核對目標沒有變更；先標記已嘗試，再呼叫一次 click。
6. 固定期限內只讀取等待；完整選票快照的 eventId、eventName、日期與時間都符合才回傳。sessionId 是抵達後讀出的值，不宣稱事前已知。

`TicketPlusSessionError` 只含固定原因及 `before-click`／`after-click-attempt` 階段，不含原始 Playwright 錯誤、個資或頁面內容。
click 拋錯、導頁逾時或未知結果均不重新點擊，不改選其他場次。
「已嘗試」不表示事件一定送達，更不表示訂單已提交；沒有發出 Klook CONTACT_SUBMISSION。
本模組保證單次呼叫最多一次 click，跨呼叫防重複與 worker 狀態留給未來 runner。

預設 clickTimeoutMs=5000、arrivalTimeoutMs=15000、pollIntervalMs=100；選票抵達期限從 click 成功回傳後計算，不隨輪詢重設。
初始與點擊前讀取、按鈕 `isEnabled` 檢查各自以 clickTimeoutMs 為上限；並非整個函式共用一個總期限。
同活動尚未跳轉、頁面暫缺資料、換頁中的讀取失敗可在抵達期限內繼續唯讀觀察；已關閉頁面、錯站／活動網址、已知但不符的完整頁面立即停止。
遇到 queue、information、checkout 不繼續操作，不稱作售完。
沒有新增登入彈窗判讀；普通 click 遇到遮罩時會逾時並保守回報已嘗試，隱藏的殘留 dialog 不單獨視為未登入。

測試 `tests/ticketPlusSession.test.ts` 使用兩個固定目的地的場次：A 導 session-A／20:00、B 導 session-B／21:00，與測試目標設定無關。
按錯 A 不會由 fixture 提供 B 的正確答案。場次名稱 B 刻意與活動名稱不同並含正則特殊字元。
選票落地 fixture 所有張數為 0，獨立紀錄各場次、tab 及其他控制項的實際 click。
涵蓋重排、隱藏副本、同時間停用重複列、受控 DOM 變動、延遲導頁、不導頁、錯場次、未知頁與遮罩。
人工測試沒有證明多場次實站版型或完全消除重驗與 click 間的最後瞬間競態；接入正式流程前仍須實站驗證。


## 選擇票種與調整張數

`src/platforms/ticketplus/ticketQuantity.ts` 提供 `selectTicketPlusTickets(page, settings, verifiedSession, options)`。
`verifiedSession` 由上一階段回傳的選票頁快照提供 eventId、sessionId、eventName、date、time；不使用其中的舊票數。
設定與識別資料在入口複製並檢查是否一致。每次取樣都重新核對目前頁面身分、完整票種列與張數。
未接入正式 runner/API，不新增候補順位，不變更既有設定、Klook 或啟動保護。

票名採完整、大小寫與全半形敏感的相等比對，不摺疊內部空白；例如「Ａ區」不等於「A區」或「Ａ區 一般票」。
目標必須唯一，不能先排除售完／停用列再消除同名歧義。非目標票種若非零立即停止，不代清票。
加減按鈕仍用同列 `getByRole("button")` 配合 mdi-plus/minus；沒有 name="＋" 假設。
名稱欄含庫存與價格，因此候選列用 XPath 比對直接文字節點；引號透過 XPath literal 編碼，不將文字拼成可執行指令。
XPath 的空白正規化只協助候選定位，正式快照仍精確比對原票名；候選不唯一則停止。也將上次確認張數綁進 locator，避免舊索引／張數變動後改點另一列。
本版適用已觀察的單一直接票名文字節點；若網站把名稱拆成未知結構，停止而不改用模糊匹配。

調整規則：

- 起始 0、目標 2：固定方向為增加，最多嘗試兩次；每次必須確認精確 +1。
- 起始 3、目標 2：只需減號可用，加號停用不阻止減票。
- 起始已是 2：完整核對後零點擊回傳。
- 已確認 1 張卻又讀回 0：停止，不重新計算差額。
- 單擊由 0 跳到 2：停止，不當成完成，也不反向修正。
- 按完仍是原值：在單次確認期限內唯讀等待，不補按。缺資料、跳值、其他票種變動、錯場次、排隊或換頁都停止。
- 初始差額是本次 click 上限；方向、次數上限及總期限不因更新重設。
- 明確售完可停止；所需方向按鈕停用回 button-unavailable，不能稱售完。未知庫存／熱賣中不保證可加票，也不計算 target > remaining 或剩餘減已選。

`TicketPlusQuantityError` 包含固定的 reason、before-click／after-click-attempt、attemptedClicks、lastVerifiedQuantity。
嘗試次數在呼叫 click 前增加；此後任何失敗都保留已嘗試階段，不在每輪歸零。
最後確認張數不是錯誤發生當下的保證。例如先確認 1 張、第二下結果不明，保留最後確認 1 張及嘗試 2 次，交人工確認，不補按、不歸零、不刷新。
即使網站逾時後才更新，舊操作也不會追加點擊；不明結果後不能把再次呼叫包裝成安全自動重試。

預設整段 timeoutMs=30000、clickTimeoutMs=3000、changeTimeoutMs=3000、pollIntervalMs=100。
整段期限在設定驗證後開始，各次 click／確認等待均受剩餘總時間限制；不自行假定平台限購上限。
逾時的 DOM evaluate 可能仍在收尾，但只讀，不含後續點擊。重驗與 click 非原子操作，不能排除最後瞬間網站或人工變動。

成功回傳完整選票快照，僅表示當次核對通過；不代表預留成功或已購票。
nextEnabled 只回報觀察值，不取代票種與張數驗證。不按下一步、不更新票數、不執行候補或錯誤恢復。

測試 `tests/ticketPlusQuantity.test.ts` 配合 `tests/fixtures/ticketplus/quantityPage.ts` 使用各票種獨立的固定加減行為與 click 計數。
fixture 不取得 production target，expected 手寫，張數另以 fixture 的 textContent 讀取，不把正式 reader 當唯一裁判。
涵蓋 0/1/2/3→2、完整票名／引號／全形差異、隱藏副本／重排／新增同名列、停用方向、庫存文案、跳兩張、錯票更新、部分完成／總逾時、延遲 ack、歸零、換場次及排隊。
延遲 ack 測試會先觀察到至少一次等待讀取，才釋放第一個更新，並檢查 ack 前第二 click 不存在。
下一步與更新票數有獨立計數，應始終為零。
以上異常與多張數案例為本機防禦測試；未實站驗證限購、庫存含義、超額提示或延遲更新規則。

## 選票提交、排隊等待與失敗彈窗

`ticketSubmission.ts` 的 `submitTicketPlusSelection(page, settings, selection, options)` 接收前一步選票快照。
設定與快照先複製核對，再重新讀頁面。目標票種完整且唯一、張數符合、其他票種零張、活動與場次一致，才允許下一步。
下一步限定在目標票種／張數的選票結構，排除資料頁與排隊標題，並固定當次按鈕節點；換頁不會重新解析成另一頁同名按鈕。
單次呼叫最多一次提交嘗試、一次關閉嘗試，兩個額度在各自 click 前消耗。此模組尚未接入 runner/API，不保證跨呼叫去重。

提交後同活動／場次的 order、confirm 才允許等待。暫時 incomplete-data、page-changed、read-failed 可等待；錯網址、頁面衝突、歧義、關閉頁面或卡住讀取均停止。
排隊消失回選票時，票種／張數仍須符合；不重送、不重新加票。進入同場次 information 才回傳，僅代表辨識到資料頁；聯絡欄位可缺漏，不代表個資或預留票數已核對。

預設 preflightTimeoutMs=5000、submitWaitMs=10000、queueWaitMs=600000、totalTimeoutMs=615000、clickTimeoutMs=3000、closeTimeoutMs=3000、readTimeoutMs=2000、pollIntervalMs=500。
總期限在輸入驗證時建立，初始提交期限從 click 嘗試前起算。首次看到 queue 才建立排隊期限，之後消失／再現不重設；所有期限取剩餘總時間限制。
關閉期限從失敗處理起算，也受總期限限制。唯讀 Promise.race 逾時會結束本次操作，不再啟動新讀取；click 使用 Playwright 自身 timeout，不用外部 race。

### 失敗彈窗的證據範圍

本次彈窗結構與文案參考 [tickets_hunter 9e2d1061 的實作](https://github.com/bouob/tickets_hunter/blob/9e2d1061b48706076943b1059616347c389df809/src/platforms/ticketplus.py#L1363-L1531)，**尚未在本次實站操作中觀察失敗彈窗**。
本機 fixture 是依上游重建的防禦案例，不是實站 HTML。正式接通前仍須複核排隊外框、失敗訊息與關閉效果。
支援 `[role="dialog"]`、`.v-dialog`、`.v-dialog__content` 內可見內容；空外框、透明或隱藏祖先不算可操作彈窗。
同一巢狀彈窗取有內容的最內層候選；如果按鈕位於外層而無法唯一定位，停止不向外猜。兩個獨立失敗彈窗或附加未知彈窗均停止。

訊息只在彈窗內讀取，排除按鈕文字；去除空白與常見標點後採完整白名單比對，允許「購票失敗」加另一條白名單訊息的組合。
「您選擇的票種已售完」「已售完」分類 sold-out；「購票失敗」「別人搶先一步」「已無可配座位」「本活動有限制購票總張數」「已被購買」「無法購票」分類 purchase-failed。
不套用上游寬鬆全文 includes；新增前後說明、問句或未知文案回 blocking-dialog。系統忙碌、請稍候不能稱售完。
沒有失敗時，只接受已觀察的完整排隊標題作為排隊彈窗內容；其他結構保守阻擋。未知自訂 overlay 可能不在這些 selector 內，不能宣稱完整偵測。

失敗狀態只適用 order。提交前已有彈窗就停止，不關閉；提交後僅同場次允許關閉。confirm 與彈窗並存不報成功。
同 order 的明確失敗優先於排隊；固定分類與 messageKey 回傳，不帶出未知彈窗全文或個資。
關閉只能使用該彈窗內唯一可見且啟用的「我知道了」「知道了」「確定」「OK」「Ok」。沒有候選、重複、模糊名稱或目標變動都停止。
點擊前重讀快照，固定彈窗及按鈕節點，原始內容比對僅留在瀏覽器內；不 force、不補按。
讀取與點擊不是原子操作：同一節點在最後瞬間被網站改用途的競態仍無法完全排除。

偵測失敗後永不轉回成功。重新核對時已確認彈窗消失才記 disappeared（未嘗試關閉）；無法定位或核對則保守回報未確認；點後重讀確認沒有失敗或未知彈窗，且仍是同 order 的選票／排隊頁才記 confirmed。
只看到舊節點 detached 不算成功，重建相同失敗彈窗仍等待至期限；關閉導頁或無法確認時維持 unconfirmed，不重試。
`TicketPlusSubmissionError` 記固定 reason 及 progress：submitAttempted、dismissAttempted、sawQueue、failure、dismissal。
所有失敗結果均停止。關閉後不 reload、不按更新票數、不換候補、不點資料頁下一步。

### 本機驗證

`ticketPlusSubmission.test.ts` 使用獨立 click counter 與 route request 次數，固定場次與固定 handler，不從正式 failure 常數產生預期答案，不用正式 reader 作唯一裁判。
資料頁下一步刻意啟用；測最後核對後換頁、排隊消失／再現、失敗與排隊共存、巢狀外框、隱藏殘留、兩彈窗歧義、關閉逾時與替換、晚到更新、無刷新重送。
共用 reader 增加 blocking-dialog／order-failure 後，既有場次的可見未知彈窗改為點擊前停止；隱藏彈窗仍不阻擋。張數調整遇新失敗狀態也是零操作停止。

## 提交結果契約

`submissionOutcome.ts` 的 `runTicketPlusSubmission` 將提交結果整理成四種終局：
information-ready（同場次資料頁）、rejected（明確失敗，另保留關閉狀態）、stopped（未嘗試提交即停止）、unknown（已嘗試但結果未確認）。
不是付款成功，也沒有任何重試。底層仍可直接使用原本 `submitTicketPlusSelection` 的快照／錯誤介面。
提交／關閉嘗試在 click 前記錄並通知；通知只拿凍結複本，同步拋錯或非同步拒絕均不改變購票行為。
結果層先保存狀態再通知外部，未知例外不會將已嘗試退回未提交。通知後仍重新檢查剩餘時間。
這是單次呼叫的記憶體狀態，並非跨程序訂單紀錄；runner 與持久占用鎖負責避免異常中斷後自動重跑。
結果層本身不負責 CLI、API、worker 的接線，也未改變 Klook 狀態或結果格式。

## 獨立 runner 與 CLI

`runTicketPlus.ts` 串接現有場次、票種張數及提交模組，只到 information-ready。CLI 使用獨立 TicketPlus JSON 設定；設定和互動終端驗證完成後才取得共用購票鎖。人工登入並按 Enter 後仍由正式選場次模組重新核對活動。沒有 cookie 登入判定或自動登入。

Chrome 使用獨立持久目錄，WEBDRIVER_EXPERIMENT 僅值為 1 時開啟既有實驗參數。流程停止後保留瀏覽器；流程結束且 context 關閉才釋放占用。啟動失敗則直接釋放；異常退出保留鎖，沒有自動清鎖或重啟購票。CLI 只輸出固定階段／結果，不輸出頁面全文或原始例外。

驗證使用本機攔截頁面串接真正 DOM 模組，確認提交一次、資料頁下一步零點擊、失敗關窗停止、無刷新，以及兩種關閉順序的占用釋放；未做網站實購驗證。既有未知／排隊狀態由提交模組處理。API、worker、GUI 啟動分流及資料／付款頁操作留待後續。

### CLI 停止原因

啟動錯誤區分購票占用尚未解除、占用建立失敗、占用驗證失敗、設定與互動終端問題；未知例外只顯示固定訊息，不轉印原始錯誤。占用存在不代表已確認原程序或瀏覽器仍存活，CLI 不自行判定殘留鎖、更不清鎖。

選場次停止保留 `TicketPlusSessionError` 的 reason 與 before-click／after-click-attempt，CLI 顯示中文原因、需要核對的設定，以及是否已嘗試立即購買。停用按鈕不等同尚未開賣或售完，已嘗試點擊也不表示尚未操作過活動頁。此變更只改善診斷，不新增開賣等待、重按或刷新。

## Worker 與狀態格式準備

`purchaseWorker.ts` 依平台呼叫既有 runner。TicketPlus 不驗證 Klook 聯絡資料，顯式傳遞 WEBDRIVER_EXPERIMENT；Klook 保留原本聯絡資料驗證、遮罩及提交判定。`PurchaseRuns.start()`、公開購票 API 與模擬入口仍拒絕 TicketPlus，本階段沒有 GUI 啟動或登入確認 API，也不改請求指紋。

TicketPlus worker 的 `waitForLogin` 先安裝接收器與頁面 close/crash 監聽，再回報 `ticketplus / login-ready` 及本次隨機 confirmationId。父端可用 `{type: "confirm-ticketplus-login", confirmationId}` 確認一次；提早、錯 ID、錯型別、重複或等待結束後的訊息不會啟動選票。`waiting-for-login` 只是進度，不代表接收器已就緒。確認不是登入成功判定，正式場次模組仍重新核對頁面。CLI 的 Enter 交接維持原樣。

本機層新增 TicketPlus 專用事件，不修改 Klook core 狀態或模擬事件。worker 只送必要事件及固定結果訊息，提交嘗試先記錄再通知；information-ready 映射到新的同名終態，rejected/stopped 映射 failed，unknown 保留 unknown。完整 information 頁面物件不送入 IPC。CLI 與 worker 共用 application 層的純訊息函式，保留場次停止的具體原因。

主服務接收、磁碟 schema、可關閉資格及共用結果文案已準備接受 information-ready；新 TicketPlus 事件／結果不當成 Klook 狀態。到資料頁後仍保留瀏覽器與占用，瀏覽器關閉後才 finished；父服務失聯仍直接終止程序，不解除異常占用。

跨程序測試直接 fork 正式 worker，測試 bootstrap 只替換 browser launch，連到測試父程序持有的本機 Chromium，全部網站請求攔截，不使用私人 profile。fixture 固定活動、場次、票種與導向，獨立保存實際點擊／網路計數，驗证交接、排隊、明確失敗、未知提交、關頁/crash、失聯、環境開關與鎖收尾；不以假 runner 回傳成功作唯一判斷。

## API 啟動與人工登入交接

`POST /api/purchase` 與 `PurchaseRuns.start()` 已依平台分流。兩平台均核對 expectedActivity 與已保存設定；Klook 保留聯絡資料驗證、v4 的 `{activity, contact}` 指紋及開賣時間檢查。TicketPlus 不讀取聯絡資料檔、不接受 expectedContact（含 null）、內部 start 也拒絕非 undefined 的 contact，不向 worker 傳 contact；指紋為 `{activity}`，排程設定可保存但尚不能啟動，詳見下方排程設定章節。

同 requestId 先查既有紀錄再檢查占用，相同條件回原結果，改平台／活動／設定拒絕。模擬仍只支援 Klook。經 API 可開啟 TicketPlus 瀏覽器並停在 login-ready；GUI 按鈕與設定表單尚未接入。

本機整合測試使用正式 API、主服務及 worker，全部網站請求攔截，核對等待期間零購票操作、並行開始與重送僅一個 worker、無聯絡檔／損壞聯絡檔均可啟動、模擬與不符設定仍拒絕、關窗後釋放占用。Klook 舊 v4 指紋以固定常數紀錄驗證，不使用新版計算函式生成預期結果。

`GET /api/purchase` 與 SSE 的 snapshot 只有現行 TicketPlus worker 已公告 login-ready、仍連線且正在等待時，才提供 `loginConfirmation: {confirmationId}`。人工登入後，以相同 token／來源防護呼叫 `POST /api/purchase/confirm-login`，body 僅包含 `{runId, confirmationId}`；runId 使用 snapshot.id（包含時間前綴），不能使用開始請求的 requestId。這不是網站登入成功判定，後續仍核對活動、場次與選票資料。

確認資格先消耗、保存嘗試紀錄，再傳送一次 IPC；並行或重複確認拒絕。傳送回呼成功回 `status: "sent"`，只代表送出，應繼續讀取狀態。IPC 錯誤、斷線或 5 秒逾時不恢復資格、不自動重送；確認 API 不回 notAccepted，也不能因此另開購票。紀錄寫入失敗時不傳送並終止 worker，保留事故占用。舊磁碟事件或服務重啟不能恢復確認資格。

成功流程停在 information-ready，沒有勾條款或操作資料頁下一步；失敗／售完及未知提交沿用原結果、不重試。流程結束後使用既有 close-browser API 關窗收尾。驗證涵蓋正式 API 到資料頁、確認競態、歷史紀錄失效與寫入故障；IPC 故障採邊界注入，未執行實站購票。

## 多順位設定與歷史紀錄相容

TicketPlus 活動設定只接受 `targets: [{date, time, ticketType, quantity}, ...]`，順序與重複目標均保留。舊 `target` 活動設定不再接受，兩者並存、空清單或任一順位無效均拒絕。內部 `TicketPlusSelection.target` 表示一次 DOM 操作的目標，仍保留。

舊 target 活動檔會列入 invalidFiles；load、同 ID 更新和刪除均拒絕，CLI 舊 JSON 也不能啟動。需要自行將檔案中的 target 物件改成 targets 陣列；程式不自動改寫或刪除私人檔案。活動檔容器仍為 schemaVersion 3。

本階段只準備設定，尚未實作候補切換：可保存多順位，但 CLI、API 新啟動及 runner 在建立占用／啟動瀏覽器前明確拒絕多順位，不會默取第一筆。既有單順位仍可購票。DOM 模組改接 `TicketPlusSelection` 單次目標，runner 明確選出後交付；不是讓各模組自行決定順位。提交售完／失敗關閉彈窗後仍停止，unknown 不重送。開賣與提前刷新設定可保存，但執行尚未接通，規則見下節。

TicketPlus 新請求使用 fingerprintVersion 5，Klook 保持 v4。重送舊 TicketPlus v4 請求時，僅無排程的單順位設定能投影成原 target 格式核對舊 hash；吻合返回原結果，不建立新程序或占用。不改寫歷史請求，活動 settingsHash 同樣依來源版本核對，單純格式轉換不會變成「設定已更新」。新請求先檢查歷史去重，再檢查本階段能力限制。

驗證保留舊單目標頁面 fixture，另外使用手寫舊活動／執行紀錄及固定舊 hash，核對只讀不改檔、同 ID 保存、新設定重播舊請求、舊設定輸入拒絕、改張數／加順位拒絕舊請求，以及多順位拒絕時零啟動。所有購票流程驗證使用本機攔截頁面，沒有實站購票。


## 開賣與提前刷新設定（尚未執行）

TicketPlus 可選填 `saleSchedule`，其中 `saleAt` 與 `advanceSeconds` 皆必填。例：

```json
"saleSchedule": {
    "saleAt": "2026-10-20T12:00:00+08:00",
    "advanceSeconds": 1
}
```

`advanceSeconds` 只接受數字 1 或 2，不自動補值；立即執行則省略整個 saleSchedule。saleAt 要包含秒與 +08:00 且日期存在，可以保存過去時間；演出日期／時間保持獨立。共用時間驗證不改 Klook 的預設秒數或刷新策略。

本階段沒有等待、倒數、刷新或 GUI 新欄位。CLI/API/runner 新啟動若帶排程，在新占用、worker、瀏覽器之前明確拒絕，不會忽略時間立即購票。新請求仍先辨識既有紀錄，再檢查能力；活動列表可讀排程，不把不可執行誤當無效設定。

無排程 v5 指紋維持原樣；排程兩欄均納入 v5 指紋與活動狀態比對。v4 舊單目標投影僅允許無排程，避免把新時間或提前秒數丟掉。固定 v4/v5 歷史指紋、真實存檔重讀與各入口零啟動測試驗證此契約；實際刷新時點的行為與測試留待後續。


## 最長時間設定與全程期限

TicketPlus 可選填 `maxRunMinutes`，只接受 1～1440 的整數分鐘。未填不補預設值；0、負數、小數、字串、null 或超上限均在取得新占用、啟動 worker／瀏覽器前拒絕。設定保存與讀取保留此欄位；舊設定沒有欄位時保持原格式與指紋。含期限的設定不能投影為舊 v4 單目標指紋，新 v5 指紋納入期限；修改期限不能沿用相同 requestId 當成同一請求。

計時從人工登入交接成功後、選場次之前開始一次，使用單調時鐘。人工登入等待不計入；場次、順位、張數、提交與排隊共用期限，換階段不重設。每次讀取、等待與點擊取原有操作／階段剩餘時間及全程剩餘時間的較小值；到期不把 timeout: 0 傳給 Playwright。沒有期限時保留原有階段限制。開賣排程執行仍未接通，不能因設定期限繞過能力保護。

手動停止與到期分別記錄 `user-stop` 與 `time-limit`，第一個已觀測的停止原因保留。唯讀操作與輪詢可被期限喚醒；已發出的點擊等待有界收尾，不用外層競速提早回報並遺留點擊。實際收尾仍受瀏覽器與程序排程影響，不能承諾精確在某一毫秒終止。

到期後不開始新操作，保留 submitAttempted、排隊、失敗與彈窗處理事實：提交前為 stopped，提交後未確認為 unknown，已辨識失敗為 rejected。已核對到 information-ready 的結果不被稍晚到期覆寫；停止後晚到的頁面也不追認為成功。瀏覽器與購票占用仍保留，流程已結束且瀏覽器關閉後才釋放；到期不是取消網站訂單。

本次只接入期限核心與既有設定／執行入口，不新增 GUI 欄位、停止 API、重試、刷新或付款操作。驗證使用可控時鐘與本地 DOM，檢查跨階段期限、實際點擊次數、在途操作收尾及舊紀錄相容性，不進行實站購票。


## 手動停止 API 與 worker

`POST /api/purchase/stop` 僅接受 `{runId}`，沿用本機 token 與來源防護。runId 是本輪 snapshot.id，不是開始請求 requestId。只控制本服務目前持有且仍連線、執行中的 TicketPlus worker；不要求 browserOpen，因此啟動瀏覽器途中也可提出停止。Klook、歷史紀錄或其他輪次不能使用這個入口。

GET／SSE 的 `canStop` 與 `stopRequest: {status}` 由本輪記憶體狀態產生，不從磁碟恢復。首次接受停止先固定請求並封鎖登入資格，再傳送一次 IPC；並行或重複請求沿用既有狀態，不重送。晚到的 login-ready 不重新開放登入確認。若登入確認已先送出，停止只能阻止後續操作，不能撤回先前動作。API 修改請求仍依序處理，停止不是立即搶占。

停止請求狀態為 sending、sent 或 unconfirmed。sent 只代表 IPC 傳送完成；錯誤、斷線或逾時為傳送未確認，可能稍後送達，不能據此恢復登入、重送或另開購票。購票 status 仍由 worker 終局回報決定，停止 API 的回覆不能覆蓋已核對的 information-ready、已提交的 unknown 或已知失敗。

worker 在開始非同步工作前安裝 TicketPlus 停止接收器，透過 AbortController 傳入現有 runner；登入等待、DOM 讀取及在途操作沿用停止核心。runner 結束後移除停止接收器，保留人工 close-browser 通道。停止不主動關閉瀏覽器、不取消網站訂單、不提早釋放購票占用；正常收尾仍須流程與瀏覽器都結束。

停止請求不新增寫盤前置條件，以免磁碟失敗阻擋停止。最終事件與結果仍遵守既有保存／異常政策；若紀錄寫入失敗導致程序被終止，不能宣稱合作式停止已完成或結果已保存，也不能承諾異常時瀏覽器一定保留。本次不新增 GUI 按鈕、重試或刷新。

## 明確售完後的重新選票前核對（尚未接入 runner）

`inspectTicketPlusReselection` 是一次性的唯讀核對，輸入必須來自同輪剛完成的提交結果、該輪已核對的場次及原有 `TicketPlusRunControl`。目前結果型別不包含嘗試識別碼，因此呼叫端負責同輪配對；不能從歷史紀錄或上一輪失敗恢復重新選票資格。

只有已嘗試提交、結果為 rejected／order-rejected、失敗為 sold-out，且彈窗已 confirmed 或 disappeared、沒有停止原因時，才讀取最新頁面。一般 purchase-failed 包含限購與模糊失敗，本版全部拒絕，即使提示為「別人搶先一步」也不例外。模組不改既有失敗分類或關窗行為，不補按關窗。

最新頁面必須是完整的同活動、同場次選票頁，核對 eventId、sessionId、活動名稱、日期及時間，且所有票種的 selectedQuantity 都是 0。這不是剩餘庫存為零；全部售完仍可能符合重新檢查的前提。零張時下一步正常可停用，因此不以 nextEnabled 或是否有票作為放行條件。排隊、資料頁、付款頁、未知彈窗、資料缺漏與殘留張數均不能放行。

核對共用原本停止／全程期限，另有預設 2 秒的局部讀取上限；既有結果帶 stopReason 時回傳 blocked 並保留原因，核對途中控制器停止則拋出原 TicketPlusStopError，交由既有停止處理收尾。不重新計時、不輪詢至成功、不修改原提交進度。ready 只是瞬間觀察，不是未來點擊許可。後續循環仍須重新驗證 DOM，重新選票時使用 requireZeroInitialQuantity: true，避免第一順位沿用晚到的殘留張數。

本版僅準備模組及本地「正式提交→售完→關窗→核對」整合測試。正式 runner 尚未呼叫，仍維持失敗後停止；不清票、不更新票數、不刷新、不切換順位或重新提交。關窗後清零的 fixture 只驗證該狀態的處理，不代表實站一定會自動清零；既有關窗後保留兩張的 fixture 行為保留。

## 單次更新票數（受限交付，尚未接入 runner）

`refreshTicketPlusTickets` 只做單次更新操作。先讀完整同場次選票頁，要求所有已選張數為零，再定位唯一可見的「更新票數」按鈕，固定節點並重新核對後最多點擊一次。原生點擊、唯讀核對受本地上限及原全程期限約束，停止或失敗都不補按。

現有觀察沒有可靠的更新完成訊號。本版點擊後會讀取畫面檢查異常，但即使仍為完整同場次零張頁，也只回 `completion-unverified`，不將舊 DOM、庫存變動或固定等待當成更新完成。結果型別目前刻意沒有成功分支，不開放下一輪選票；這是單次操作與停止核對，不是完整刷新循環。之後取得實站完成訊號才增加完成等待與成功結果，不提供 fixture 專用成功開關。

是否更新由上層策略決定：設定的目標票種全部明確售完，或本輪順位耗盡即可進入更新流程，非目標票種仍有庫存不影響。這與操作前「所有已選張數為零」不同；上層不能將未知庫存、缺列或歧義當作全部目標售完；非目標有已選張數也會阻擋操作。單次更新模組本身不判斷可售庫存。此模組不清票、不選票、不提交。

本地 Playwright 測試核對實際點擊次數、隱藏副本、歧義、殘留張數、錯場次、未知彈窗、讀取取消／逾時與遮罩點擊逾時。沒有實站更新完成驗證，也未捏造完成訊號。

## 同場次順位循環（單輪候補與耗盡後受限更新）

`runTicketPlusCycle` 接入正式 runner，使用同一瀏覽器、場次與停止控制。選票仍只看設定 targets：目標 A/B 都明確售完時，非目標 C 還有庫存不阻擋進入更新；但 C 有已選張數或任何票列無法完整辨識仍停止。熱賣中庫存 null 不等於零，停用加票、缺票名、歧義與一般購票失敗不能當售完。首次選票保留原有補差張數行為。

某順位提交後，只有明確 sold-out 且關窗後重新核對通過，才從下一個原始順位繼續；每次再選都要求初始已選張數全部零。同一輪每個設定順位最多提交一次，不額外重試同順位、不清票、不跨場次。殘留張數／一般失敗／限購／未知提交結果都停止。到同場次填寫資料頁即完成，不操作資料頁、條款或付款。

目標全部在畫面明確售完，或各順位在本輪曾明確售完而耗盡，會等待 1 秒（可停止且受原全程期限限制），再呼叫單次更新模組。兩種耗盡來源分開處理，不捏造提交結果；「本輪耗盡」也不表示最新庫存一定同時全零。目前更新結果沒有成功分支，最多更新一次後明確停止，尚未啟用跨輪持續刷新或宣稱完成驗證。此處的一秒只是操作間隔，不是更新完成判定，不是開賣排程。

當次 progress 與整趟 submissionAttempts 分開保存。售完且重選核對通過後發出內部 attempt-reset，runner/worker 同步清除舊 failure，但不清除整趟曾提交的事實。A 售完後 B 結果不明仍是 unknown；輪間停止則說明先前已確認售完，不錯稱從未提交。共用事件新增 waiting-to-refresh / refreshing，僅記錄安全進度，不傳完整頁面資料。占用仍在流程結束且瀏覽器關閉後才釋放。

本地 fixture 重建真點擊／關窗／張數與頁面跳轉，涵蓋 A→B、前順位略過後 B→C、非目標庫存不影響更新、殘留與未知阻擋、期限／停止及 runner/worker 接線。fixture 關窗清零只是防禦情境模擬，不證明實站一定清零；更新完成與跨輪成功仍未實站驗證。

## TicketPlus 三步驟介面

活動工作區沿用 Klook 的步驟列樣式，分為「活動與順位」、「確認與開始」、「執行狀態」。進入活動先顯示第一步；儲存成功接受伺服器回傳的 ID、版本與設定後前進第二步，列表刷新失敗僅顯示警告。保存驗證失敗或版本衝突保留第一步草稿。第二步只顯示已保存摘要；回第一步修改後仍須重新儲存才可啟動，切換步驟不隱式保存或開始。

正常啟動成功後留在工作區第三步，提供原有登入確認、手動停止與關窗操作。全域執行狀態與同步鎖仍由 App 唯一持有，切換步驟不重新建立訂閱或控制資格；保存／開始／查詢送出中禁止步驟導覽，購票占用期間可以查看已開啟的步驟，但不能變更設定或開始另一輪。

第三步只顯示這個工作區成功啟動所取得的 runId，另開活動會清除本地關聯；尚未啟動不能把全域舊紀錄當作本活動結果。執行快照沒有活動 ID，因此不以名稱推論關聯，也不新增跨重新載入的步驟／草稿恢復。首頁查看目前狀態與待確認啟動結果仍使用全域狀態頁，避免將其他活動的結果套入目前三步驟。

本地測試保留既有保存、版本衝突、pending 與跨平台防護，並以實際保存資料、購票請求與本地 worker 行為驗證三步驟。測試導覽不自動保存，避免抹掉未保存修改等負向案例的前提。本次不變更設定格式、購票 runner 或開賣排程能力。

## 開賣等待核心（歷史第一版，已由下方提前刷新核心取代）

TicketPlus 的 saleSchedule 可省略 advanceSeconds，表示僅等待 saleAt、不刷新頁面。明確設定 1／2 秒仍可保存讀取，但目前拒絕啟動；不默默忽略提前刷新。Klook 缺省提前 1 秒的規則不變，歷史單目標指紋投影仍拒絕排程。

## 提前刷新與開賣後再次刷新

有 saleSchedule 時，缺少 advanceSeconds 在執行時預設為 1 秒，也支援明確的 1／2 秒。解析與保存不自動補寫缺省欄位，以保留既有設定指紋、未確認請求與重播相容性；沒有排程仍沿用立即開始流程。

人工登入交接後等到開賣前指定秒數刷新活動頁一次。交接較晚但尚未截止則立即刷新。刷新成功後核對活動名稱、ID、唯一目標日期與時間；開賣前即使按鈕已可買仍等待，到點重讀。開賣後只有明確的「尚未開賣」可觸發再次刷新，兩次刷新起點至少相隔 3 秒。可買時離開等待，交由既有選場次流程一次操作；點擊失敗不返回刷新迴圈。

截止固定為 saleAt 加 2 分鐘，且單調時鐘上限防止回撥延長等待；刷新次數不重設期限。API 對過期的新啟動要求拒絕，但既有 requestId 的結果重播優先。runner 在人工登入後也核對截止。maxRunMinutes 在開賣準備完成、選場次前才開始，不包含人工登入與開賣等待。

刷新前要求仍在設定的活動網址，不能刷新選票、資料頁或其他活動。HTTP 錯誤、刷新逾時、活動不符、歧義場次、停用的立即購買或不明畫面均停止。資料缺漏只允許短暫唯讀等待，不把空白當成尚未開賣；沒有可靠開賣後狀態便不補刷。刷新是已送出的瀏覽器操作，停止後仍等待這次操作收尾，再結束；不發起新的刷新或購票點擊，瀏覽器仍保留供人工檢查。

狀態事件分開使用 refreshing-activity（活動頁刷新）、waiting-for-availability（等待場次開賣）；原 refreshing 仍只代表更新票數。GUI 與 CLI 文案同步反映新能力，GUI 秒數選擇控制另行實作。實站只觀察到靜態按鈕，刷新、延遲載入及開賣狀態切換使用本地路由測試，尚未驗證實站完整刷新時序或登入失效版型。
