# TicketPlus 開賣時間設定

在 GUI「確認與開始」選擇立即開始，或指定開賣時間與提前秒數。活動檔可保存：

```ts
saleSchedule: {
    saleAt: "2026-10-10T10:00:00+08:00",
    advanceSeconds: 1,
},
```

上例只示範格式，不代表實際活動的開賣時間。日期時間必須完整、有效並帶 `+08:00`。提前秒數只接受 1 或 2；舊設定省略時預設提前 1 秒。沒有 `saleSchedule` 時立即開始。格式錯誤會在啟動瀏覽器前拒絕。

## 流程與界線

1. 先在 TicketPlus 首頁確認登入，再前往設定活動。未登入時等待人工登入；有排程時，登入同時受開賣後 2 分鐘的截止限制。
2. 等到指定的提前時間才刷新活動頁；已超過提前時間但尚未截止時，立即刷新一次。
3. 刷新等待新頁 `domcontentloaded`，最多 15 秒，並受剩餘截止時間限制。HTTP 失敗、載入逾時或網址不符都會停止，不使用舊畫面繼續選票。
4. 重新核對活動識別、名稱與唯一目標場次。資料未完整時最多等 5 秒；空白不是尚未開賣。已知活動提醒依每次載入的點擊額度處理，未知或矛盾畫面停止。
5. 正式開賣前，即使按鈕已可用也不進入購票。到點再次讀取目標場次，確認可購買才交給後續選票流程。
6. 只有目標場次明確顯示尚未開賣，才允許再刷新。兩次刷新起始至少間隔 3 秒；刷新前再讀取一次，網站已自行開賣時直接繼續，不多刷新。
7. 開賣準備的截止固定為 `saleAt + 120 秒`；同時以單調時鐘限制剩餘等待，系統時鐘回撥不能延長總等待。過了截止才啟動會停止。
8. 開賣準備完成後才開始計算最長購票時間，不將登入與開賣等待計入。準備流程結束時移除監聽，不留下背景刷新。

任何階段都可要求停止。頁面關閉、崩潰、活動不符、場次缺失或重複、場次停用、未知資料及刷新失敗都會停止，不當作售罄，也不增加提交重試。

## 驗證限制

時間格式與驗證集中在 `src/core/saleSchedule.ts`；TicketPlus 活動刷新與狀態核對位於 `src/platforms/ticketplus/salePreparation.ts`。活動欄位與載入階段的實站觀察見 [活動場次欄位擷取](ticketplus-activity-fields.md)。

本機 fixture 驗證等待、刷新與停止邊界，未因此證明實站開賣瞬間的完整流程。提前刷新依本機時鐘，休眠或時鐘不準仍會影響觸發時機，不保證取得票券。
