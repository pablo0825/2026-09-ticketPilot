# 易讀程式碼指南

目標是寫出初學者也能讀懂、維護與擴充的程式碼：
主流程一眼看懂，每個函式的責任清楚，需要時再組合起來。

遵循專案既有規範；與本指南衝突時，以專案規範為準。
遇到多種可行寫法時，選最容易理解的那一種。

## 程式碼原則

1. **簡單直接**：使用容易理解的寫法，不為減少行數把邏輯擠在一起。
   只解決目前的需求，不預先加入用不到的功能或複雜設計。
   巢狀判斷太深時，優先考慮先處理不成立的情況並提早 return，
   讓主要流程容易閱讀。

2. **主流程與細節分開**：主流程清楚列出步驟，
   各步驟的細節放進職責明確的函式，再由主流程組合使用。
   安排這些步驟本身就是一項清楚的責任。

   ```ts
   function createReport(rawRows: Row[]): string {
       const validRows = removeInvalidRows(rawRows);
       const totals = sumByCategory(validRows);

       return formatReport(totals);
   }
   ```

   讀主流程就知道報表怎麼產生；想了解細節時，再進入各函式查看。

3. **責任清楚**：一個函式負責一件能清楚說明的工作。
   如果混入不同用途的工作，拆開後更容易理解或修改，就把它們拆出去。

4. **適度拆分**：為了更容易理解、修改或重用而拆分，不只因為行數多就拆。
   相關的小函式可以先放在同一個檔案，避免閱讀時不停跳轉。

5. **名稱清楚**：函式名稱說明「做什麼」，變數名稱說明「存什麼」。
   避免難懂的縮寫，以及看不出用途的名稱。

6. **註解幫助理解**：較長或多步驟的流程，用簡短中文註解說明每段目的。
   不直觀的地方說明原因；不要逐行翻譯程式碼。

## 修改原則

1. **只改需要改的**：每項修改都對應目前任務，不順便重構或重排無關程式碼。

2. **保留原本行為**：重構時保留輸入輸出、驗證、錯誤處理與必要的操作順序；
   不要意外增加、漏掉或重複寫檔、送出請求等操作。要改變行為就明說。

3. **不掩蓋問題**：不用預設值或空的 catch 藏住錯誤；
   不為讓檢查通過而放寬驗證或跳過測試。

4. **不確定就先問**：會影響需求或對外行為的疑問先問清楚；
   一般實作細節，依專案既有寫法自行決定。

5. **只審查時不動手**：使用者只要求審查時，提出有依據的問題與建議，不自行修改。

6. **簡短說明修改**：完成後簡短說明改了什麼；
   有拆分時說明原因，並指出還沒確認的部分。

## 測試原則

1. **保護重要行為**：優先測試輸入檢查、計算結果與狀態變化等重要判斷，
   包含正常情況，以及容易出錯的邊界與失敗情況。

2. **修好問題後留下保護**：修復 bug 時，
   盡可能加入能在修正前抓出問題、修正後通過的測試。

3. **測試結果，不綁死寫法**：確認結果與行為符合預期，
   不要求內部一定使用特定變數或拆成特定數量的函式。
   不必為每個小函式另寫測試，也不只為提高覆蓋率而增加測試。

4. **沿用工具，確認修改**：使用專案既有工具，修改後執行相關檢查；
   簡短說明檢查範圍，以及未執行或未通過的部分。
   不為小修改引入新測試框架；不影響行為的修改可採較輕量的檢查。
